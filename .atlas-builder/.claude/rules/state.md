# Rule: State Model (META.md §8)

## Two planes, never merged

- Control plane: `CONTROL_ROOT/.agent/state/` (workspace.json, project_index.json, control_context.json, control_runs.jsonl, tool_audit.jsonl, essence_attestations.jsonl, plus high_risk_changes.jsonl as the hook's fallback when no project can be resolved). About Atlas Builder itself.
- Project plane: `PROJECT_ROOT/.atlas-builder/state/` (state_index.json, project.json, spec.json, todo.json, recommendations.json, blockers.json, context.json, validation.json, plus the three .jsonl logs: reflection.jsonl, runs.jsonl, high_risk_changes.jsonl). About the target project.

## Discipline

- Mutate state via `bin/atlas-builder state <command> --project ../PROJECT_TITLE` whenever a command exists for the transition. Your commands: ensure / validate / apply-projection / should-stop / should-complete / should-reset / status. `supervise-check --todo T-... [--recommendation R-...]` is also read-only and may be used to inspect the exact High-Risk authorization that the human wrapper enforces.
- Loop-owned commands (hook-denied to you, META.md §18.2, §19.1): start-run / end-run / record-progress / reset-context / raise-loop-gates — atlas-builder-loop.sh runs them at the cycle boundary. A mid-cycle record-progress corrupts the idle-progress signal; a stray start-run forces a false crash recovery. When you detect a stop condition, record your own precise Recommendation instead of trying to raise a loop gate.
- `atlas-builder state resume` also exists but is a human-only transition (human intervention: stop-gate release or mid-course update, META.md §13.3); never invoke it (I-011).
- Mutating commands refuse a `--project` other than the bound project (1 control plane = 1 project); do not try to ensure/seed state for sibling directories.
- Do not edit spec.json / todo.json / blockers.json / recommendations.json in place — the pre-tool guard hook now DENIES a direct Edit/Write of these four canonical projection files (matching the Bash-mutator deny that already covered `.atlas-builder/state/`), so the only path is: write a temporary JSON object whose non-empty key subset is exactly `spec.json`, `todo.json`, `recommendations.json`, and/or `blockers.json`, then call `bin/atlas-builder state apply-projection --file <bundle> --project ../PROJECT_TITLE` (the binary's own write is not an Edit/Write tool call and is unaffected). context.json and the .jsonl logs (reflection / high_risk_changes) stay directly writable, since you author those. The command validates the complete prospective state before its first write and atomically replaces each accepted file. Keep `schema_version: "1.0.0"` and unique ids (`S-###`, `T-###`, `R-###`, `B-###`; `R-LG-*` is loop-reserved).
- Every Spec item must carry a non-empty `essence_refs` string list. Each value must exactly reproduce one current human-authored content item in ESSENCE.md (ignoring whitespace runs). Validation rejects missing, stale, or fabricated refs; headings and directive lines (`deps:`/`recipe:`/`profile:`) are not trace sources. Exception by design (META.md §20.2-7): while spec.json's `projected_from_essence_sha256` drifts from the current ESSENCE.md — the human edited the Essence and you have not re-projected yet — stale refs surface as ONE aggregated drift warning (naming the affected Specs) instead of per-Spec errors; re-project Spec first. You cannot write a stale projection: `apply-projection` refuses a bundle whose spec.json is not stamped with the current ESSENCE.md SHA-256 (§20.2-8). Bundles that do not touch spec.json (e.g. recording a Blocking Recommendation about a contradictory Essence) still apply during drift.
- Every High-Risk Todo must carry a non-empty `target`; an authorizing Recommendation must list that Todo ID in `source` and repeat the exact same `target`, otherwise `just supervise` refuses before launching Claude.
- `project.json` and the control-plane attestation ledger (`.agent/state/essence_attestations.jsonl`) are NOT directly editable (hook-denied): they anchor the essence attestation chain (§13.1-10). atlas-builder state transitions maintain them. Each ledger record carries both the ESSENCE.md `essence_sha256` and an `essences` manifest (`essences/`-relative path → SHA-256 of every asset, §2.1.5); the bootstrap anchor in `project.json` mirrors this with an `essences_manifest` key beside `essence_sha256` (ensure records it). A drift of the live essences/ manifest from its baseline stops the loop as `essence_unreviewed_change`, exactly like an ESSENCE.md hash drift.
- JSONL files are append-only. Never rewrite or truncate them.
- `state_index.json` describes what is canonical; if you add a state file, register it there.
